## Post-Mortem: Falha no primeiro deploy de dev
Duração: 50 minutos
Severidade: SEV-3
Data: 04/10/2026
Status: revisado

# Resumo
As primeiras tentativas do deploy no ambiente de dev não foram suscetíveis, afetando e atrasando os testes da aplicação que, subsequentemente, atrasam o deploy no ambiente da produção. As causas foram:
- Token de acesso do Supabase usado não tinham permissões necessárias.
- HF_SPACE_ID do ambiente dev apontava para Space de produção.
- O modelo.pkl não estava no remote Azure.

# Impacto
Nenhuma para usuários da aplicação, mas causou atraso no cronograma de deployment.

# Causa Raiz
- Modelo ausente no remote Azure: o dvc.lock referenciava um data/model.pkl que não tinha sido enviado com dvc push. O dvc pull do CI falhou nos três jobs.
- Testes de autenticação e observabilidade:
  - Autenticação: `enable_signup = false` em `[auth.email]` do `supabase/config.toml` desligava o login por e-mail inteiro, inclusive para contas criadas pelo admin.
  - Observabilidade: o ci.yml desliga OBSERVABILIDADE_ATIVA no workflow inteiro e a fixture do teste não religava a variável, então o round-trip encontrava 0 linhas.
- Token do Supabase sem permissão: o runner não tem IPv6, então o db push só conecta pelo pooler. O SUPABASE_ACCESS_TOKEN não tinha *Connection Pooling: Read*, e a consulta da URL do pooler recebia 403.
- Timestamp em formato inválido: o PostgREST remove os zeross finais da fração de segundo, e o `datetime.fromisoformat` do Python 3.10 só aceita 3 ou 6 dígitos. Isso afeta cerca de 1 em cada 10 valores, resultando em testes intermitente.
- HF_SPACE_ID apontando para produção: a variável do environment deve foi preenchida com o id do Space de produção.

# O que foi bem
- A ordem CI → migration → sync impediu que código quebrado ou schema desatualizado chegasse a qualquer Space.
- Modelo ausente no remote Azure: a falha apareceu no primeiro passo do CI, antes do build e do deploy.
- Testes de autenticação e observabilidade: os testes de integração com Supabase local pegaram o erro de configuração antes do ambiente remoto.
- Token do Supabase sem permissão: a consulta explícita à API trocou a mensagem enganosa (IPv6) pelo status real (403), depois da correção para investigar a falha.
- Timestamp em formato inválido: o teste de integração expôs o bug antes da UI, e o helper que já existia para o canário foi reaproveitado.
- HF_SPACE_ID apontando para produção: o HF_TOKEN de dev, com escopo restrito, barrou a gravação. O histórico do Space de produção confirma que nenhum commit foi feito.

# O que pode melhorar
- Modelo ausente no remote Azure: nada verifica se o modelo referenciado no `dvc.lock` existe no remote antes do push do commit.
- Testes de autenticação e observabilidade: o login desabilitado aparecia como "E-mail ou senha incorretos", o que escondia um problema de configuração.
- Token do Supabase sem permissão:
  - A falha do `supabase link` é silenciosa, e o primeiro diagnóstico apontou para a rede.
  - O log não mostrava o corpo da resposta de erro (`curl > arquivo`).
  - As permissões necessárias do token não estavam documentadas.
- Timestamp em formato inválido: os testes unitários não cobriam o formato real devolvido pelo PostgREST, e a leitura de `timestamptz` não passava por um helper único.
- HF_SPACE_ID apontando para produção:
  - O isolamento entre ambientes dependeu do escopo do token, e não de uma validação de propósito.
  - Com `delete_removed: true`, um token com escrita teria sobrescrito o Space de produção.
